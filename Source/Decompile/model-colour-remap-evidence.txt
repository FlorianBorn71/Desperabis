Recovered model-colour table selection
-------------------------------------
These are indexed-colour remaps, not ascending grayscale brightness levels.
For display modes 20..25, A660 returns mode - 19. The fixed-table model draw
path subtracts one before calling 4C1C, giving selectors 0..5.

Display  Selector  DS table  OPGSET row  Colour/material family
20       0         1200      0           Water/colour-reduced remap
21       1         1400      1           Orange/fire/lava
22       2         1300      2           Very dark/oil/charred
23       3         1900      identity    Identity/fullbright
24       4         1700      4           Blue-white glass/fog
25       5         1600      3           Red lava

The loader at DCCB..DE35 explicitly constructs DS:1900[i] = i.
The Pascal strings immediately before it are LEVEL\OPREDU.256 at CS:DCA9
and LEVEL\OPGSet.256 at CS:DCBA. They are data, not instruction ranges.
After skipping each file's four-byte header, it reads OPREDU into DS:1500
and seven OPGSET rows, in order, into DS:1200, 1400, 1300, 1600, 1700,
1800 and 1A00. Rows 5 and 6 are not selected by model display modes 20..25;
their colour semantics are not inferred here.

Data\SourceAssets\Original\LEVEL\OPGSET.256 contains 1796 bytes:
four header bytes FF 00 05 00, then seven complete 256-byte remaps.
The ordinary width/height-minus-one interpretation says 256 by 6, but the
native loader ignores those dimensions and explicitly reads all seven rows.
Unique output counts for rows 0..6 are 118, 16, 18, 6, 44, 119 and 29.
Row 1 maps exclusively into palette indices 240..255; row 3 into 0..5;
row 4 into 146..221. Sampling BACKGR1.PAL corroborates the orange, dark
and red families, but is not proof of the active DOS palette in every level.
The colour-family labels also correspond to the existing renderer material
selectors Water, Lava, Oil, Identity, WhiteFog and RedLava.
Their current GetWaterTintColor RGB/alpha values are modern approximations,
not a byte-for-byte implementation of these native lookup tables.
The matching model enum names are VectorWaterTint, VectorLavaTint,
VectorOilTint, VectorFullbright, VectorBlueTint and VectorRedLavaTint.
Whole-model rendering reuses the material RGB approximations but sets alpha
to 255. Numeric IDs and core post-burning/impact behavior remain unchanged.

The blue-glass/light-ray identification is supported by real primitives:
* Level 20's behavior-73 ray object resolves to VEKT33.3DA. Bank 1, frame 5
  has five type-3 triangles with colour byte D4 and fill byte 1.
* Level 95 model ID 35 resolves to VEKT48.3DA (not VEKT47). Bank 1, frames
  1 and 2 each have six type-3 triangles with colour byte F4 and fill byte 1.
Both colour bytes have low nibble 4, matching the existing WhiteFog material.
The 3DA parsers consumed all 26377 and 5825 bytes respectively.

In normal model drawing, 8587..85B9 reads polygon byte 1 and byte 5.
For nonzero fill byte it constructs:
  colourArgument = 0200h + (colourByte AND 0Fh) + 16 * (fillByte - 1).
Thus both examples pass 0204h to the triangle rasterizer at 52A0.
This confirms that the glass/ray effect is a per-triangle selector, not a
requirement for the whole object to have display mode 24. The exported
triangle branch proves the selector/fill encoding, not every inner-raster
operation or its exact final RGB appearance.

Modes 30..36 instead select consecutive shade maps 0..6 at DS:0A00.
They are brightness/shade levels: stage 0 is brightest, later stages darken.
These are named VectorBrightness0..6 and use TintColorForBrightness with
the existing descending RGB shades 255, 223, 191, 159, 127, 95 and 63.
The former VectorFade names and the ascending grayscale ramp for 20..25
have been replaced; this is still an RGB approximation, not palette remapping.
Modes 26, 27 and 37 have no explicit case in A660 and must not be assigned
new fixed-table semantics by extending the neighbouring numeric ranges.
