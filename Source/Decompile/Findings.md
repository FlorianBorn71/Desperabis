# Executable findings

This is the starting knowledge base for gameplay recovery. It records
executable facts and unresolved interpretations, not a recovered source listing.
For setup, naming, and evidence conventions, see [README.md](README.md).

## Scope and evidence

All executable addresses below refer to the original
[DESPERAB.EXE](../../Game/Original/DESPERAB.EXE), SHA-256:

```text
219525080e93e7a9d2b072b0dd75ed35bb7e41024e01e837c7889566723a9318
```

Evidence:

- [Executable baseline](original-executable.json), generated by
  [InspectExecutable.ps1](InspectExecutable.ps1).
- [Initial Ghidra import report](initial-import.txt), generated by
  [VerifyDosImport.java](ghidra_scripts/VerifyDosImport.java).
- [Project README](../../README.md): author's account of Turbo Pascal 7.0
  and hand-optimized inline assembly. This is historical context, not a
  compiler identification independently established from the binary.

No runtime experiments have been performed. Subsequent static tracing has
identified a high-level dispatcher, gameplay-loop candidates, and the
author's object-behavior routine; see [High-level program structure](HighLevelStructure.md)
and its [instruction evidence](high-level-evidence.txt). Object fields are
still only partially understood.
The renderer's existing accessors and the author's layout information are now
connected to the binary in [Object behavior recovery](BehaviorRecovery.md).
That page also documents the compilable named-handler scaffold. Pillar,
IdleAnimation, SmokeFading, Switch1, SwitchGrouped, and WaterDrop are implemented; other handlers remain explicit
placeholders.
The author's Excel object layout has been compared with the renderer accessors
and added as the canonical 54-byte `RawGameObject` struct in
[BehaviorDispatch.h](Scaffold/BehaviorDispatch.h). Every named offset
is compile-time checked. Dispatch and handlers take the struct directly by
reference and use its members without field snapshots. See
[Fixed-layout RawGameObject](BehaviorRecovery.md#fixed-layout-rawgameobject)
for known meanings, uncertain fields, and binary inspection helpers.

The first explained behavior case is now [Pillar](Pillar.md): it writes `38h`
to a grid through a far pointer at DS:`69C4`, converting X/Z at 25 raw units
per sample. Its [C++ helper](Scaffold/CollisionMap.cpp) and
[Pillar handler](Scaffold/BehaviorHandlers.cpp) are implemented and host-tested,
but not yet validated against a DOS runtime capture.

### Named shared collision-map helpers

| Module-relative entry | Recovery name | Contract |
| --- | --- | --- |
| `10AC:387B` | `SetCollisionMapPixelAtWorldXZ` | Converts world X/Z and overwrites one map byte with its supplied value |
| `1E48:CF49` | `GetCollisionMapPixelAtWorldXZ` | Converts world X/Z and returns one map byte through the lower-level reader at `1E48:0E8F` |

Use these names consistently for future callers; they are not Pillar-specific.
See [Pillar: shared helper name](Pillar.md#shared-helper-name) for stable
identity, Ghidra address, parameter layout, and current caller evidence.
Preserve original parameter interfaces as closely as evidence allows; see
[Function parameter fidelity](README.md#function-parameter-fidelity).
In particular, the writer has three word-sized argument slots in X, Z,
value push order, with `RETF 6` cleanup; only the value's low byte is read.
That does not establish its original Pascal source type.

The reader has two word arguments in X/Z push order, returns a byte in AL,
and uses `RETF 4`. **Confirmed caller:** behavior 11 (`Behavior_11`) at
`0000:1580`. It tests the returned byte's low three bits: values other than 1
change its frames and behavior to 12; value 3 also calls an unresolved helper.
The lower-level reader checks hardcoded column/row limits 0..319/0..239,
not the map's stored dimensions. A separate helper at `1E48:2A64` reads a
3x3 neighborhood and uses masked samples to adjust referenced words; its
callers remain unresolved. `GameState::GetCollisionMapPixelAtWorldXZ(x, z) const`
is implemented in [CollisionMap.cpp](Scaffold/CollisionMap.cpp), with the
original coordinate bounds, 16-bit address wrapping, and explicit host
allocation checks. Host tests cover every X/Z word independently and the
complete accepted grid plus its border across six stride headers. The 3x3
neighborhood helper and behavior 11 remain unimplemented.
See [reader details](Pillar.md#reader) and
[complete instruction evidence](collision-map-reader-evidence.txt).

**Author-provided, provisional semantics:** `CollisionMapValue_BlockingWall`
names the whole value `0x38`. Surface flags for water and grass are remembered,
but their numeric masks are unresolved. The remembered door 3x3 writer is now
identified at `10AC:3EE0`, called by the door helper at `10AC:40F0`;
see [door footprint](Pillar.md#closed-door-3x3-writer). It remains separate
from the single-pixel helper and is not yet implemented in C++.

`CollisionMap` directly contains two unsigned 16-bit words,
`widthMinusOne` and `heightMinusOne`, followed by the plain built-in array
`std::uint8_t data[VARIABLE_SIZE]` at offset 4. There is no separate header type.
This agrees with the author's recollection and the allocation evidence.
`CollisionMap` has inline `data` at offset 4, temporarily sized for 40000 pixels.
`Level` owns a heap-allocated collision-map pointer, not an embedded map.
`CreateDummyLevel()` allocates exactly `width * height + 4` bytes for the
zero-filled 200x200 map (40004 bytes, stored dimensions `199, 199`).
Variable dimensions will follow with real level loading. The layout is declared in
[BehaviorDispatch.h](Scaffold/BehaviorDispatch.h), with creation implemented
in [CollisionMap.cpp](Scaffold/CollisionMap.cpp).

### Switch behavior and shared door state

There are two confirmed mechanisms, not a single global switch mask:

- `Switch1` (50) animates phase 0..100, reverses automatically, and optionally
  latches when object byte 52 is nonzero. The ordinary interaction uses the
  switch index at byte 34: helper `10AC:2060` scans object slots 2..140 and
  activates objects with health equal to `wrap16(1000 + switchIndex)`.
- `SwitchGrouped` (51), helper `10AC:CAEC`, clears/restores bits in a shared
  **five-byte array at DS:EC70**, indexed by object byte-44 word, using the
  low byte of its byte-46 mask word. Initialization fills all five bytes
  with `FFh`. Doors read the same indexed byte and invoke their activation
  path when it reaches zero.
- Grouped switches have a real countdown at object byte 36 while phase is
  100, gated by signed-positive byte-34 and byte-36 words. Expiry restores
  the mask bits immediately and starts return animation at rate -10.

The context now contains a plain
`std::uint8_t switchGroupMasks[5]`, initially all `0xff`, rather than a
single global integer bitmask. `Switch1` and `SwitchGrouped` per-frame cases
are implemented and host-tested, including word wrapping, timer/latch behavior,
shared masks, field isolation, and explicit invalid-index errors.
Neither case needs other objects. Cross-object activation will need a shared
object collection. The large target-interaction routine and player input are
not fully recovered. Grouped timer arming/rearming is now identified in the
separate object-interaction dispatcher at `0EF0:09F8`, case `0F52`, and is now
implemented. Ordinary switch targets and the broader activation system remain
unimplemented.
See [switch details](BehaviorRecovery.md#switches-local-animation-indexed-activation-and-group-masks)
and [instruction evidence](switch-evidence.txt) for addresses, object-field
roles, and other switch variants.

### Player collision and interaction dispatch

The generic overlap query is `1E48:2B33`: a shared byte-7 mask and strict
X/Y/Z bounding-box tests using summed XZ/Y collision radii. The player wrapper
`0000:CE9E` selects one overlap with an additional preference rule. The player
update at `0000:D060` calls it at `D8D7`, then selects on the collision byte
at `D8FC`; contact responses include doors, enemies, triggers, and teleporters.
A separate dispatcher at `0EF0:09F8` also selects on collision type and includes
ordinary/grouped switch interaction. Its grouped case copies object word 34
to the countdown at word 36, resolving the timer-arming question.

See [player collision details](BehaviorRecovery.md#player-collision-and-object-interaction)
and [complete bounded evidence](player-collision-evidence.txt). Both overlap
queries and collision-selected interaction gameplay are now implemented.
The author confirms ENTER-triggered interaction, including item pickup;
the original input-gated calls are preserved in the inventory evidence.
`10AC:10F5` is a different shared target-interaction routine, not the
player-contact dispatcher.

The new `InputHandler` interface supplies virtual
`IsInteractionKeyPressed()`. Call `UpdatePlayerInteraction(context, input)`
once per update: it selects the overlapping object, stores its original slot
in `playerCollisionSlot`, and invokes the interaction handler only when the
input method returns true. No collision means no input/interaction call.
The game context owns world records alongside the separate inventory.

The original player selector's post-test loop has an edge case: if the generic
query first finds slot 164, the preference pass examines slot 165 once.
The host reserves that boundary record but does not add it to the normal
2..164 candidate range. Its original semantic role remains unknown.

See [the per-update hook](BehaviorRecovery.md#per-update-player-interaction)
and [implementation](Scaffold/PlayerInteraction.cpp). Collision queries,
signed-word geometry, preference, input gating, and pickups are host-tested.
Full player movement, automatic contact responses, world behavior scheduling,
platform keyboard polling, and UI/audio are not implemented by this hook.

### Inventory and pickup gameplay

`GameState` now owns a fixed array of **14 complete game objects**: two hand
slots and twelve backpack slots. Original slot zero at DS:`2DEC` is only a
preview/scratch object; the 810-byte initialization includes it, but it is
not an extra usable slot. The host uses a local snapshot for copying.

Implemented explicit interactions include gold, medicine stacking, keys and
generic pickups, ammo, weapon registration and duplicate handling, arrow
poison, map ownership, grouped-switch arming, and three object-local puzzle
cases. Gold (`2DCA`), arrow poison (`2DE5`), map ownership (`D4FB`), and both
32-word weapon amount/slot tables (`DD36`, `DD76`) belong to the context.
No pickup is invoked automatically by behavior dispatch.

The author identifies poison as an arrow effect, not player poisoning; its
pickup takes the maximum of the old counter and the item's value. Medicine
pickup stores/stacks the item rather than immediately healing. Keys remain
individual inventory objects, not a guessed global key bitmask.

Still unresolved: resource-table indices 20 and 23 (new-game values 1000 and
100), the meaning of the byte-4 inventory conversion, and broader UI/audio,
inventory-use, purchasing, and door/ordinary-switch integration. Unsupported
special interactions are explicitly reported, not treated as generic pickups.
See [implementation details](BehaviorRecovery.md#inventory-and-explicit-interaction),
[new evidence](inventory-evidence.txt), and
[gameplay code](Scaffold/ObjectInteraction.cpp).

Runtime types use production-oriented names: `Desperabis::Level`,
`Desperabis::GameState`, and `Desperabis::RawGameObject`. Recovery terminology
describes the investigation, not the intended identity of the game code.

### Simple object-local behavior

`IdleAnimation` (15), case `0000:1666`, has no helper calls or direct global
accesses. It advances only the blend-phase word at object byte offset 42,
using the word at 34 as a per-tick increment and the tick-count argument.
The result is a signed remainder modulo 200 after 16-bit wrapped arithmetic,
matching the renderer's ping-pong blend interpretation. See
[IdleAnimation](BehaviorRecovery.md#idleanimation-object-local-blend-phase)
and [instruction evidence](simple-behavior-evidence.txt).
The [C++ handler](Scaffold/BehaviorHandlers.cpp) is now implemented and
host-tested, including complete 16-bit rate/phase coverage at representative
tick counts and byte-level isolation of its only write. Common object-update
preprocessing/postprocessing are not claimed to be object-local or implemented.

### SmokeFading and shared math

`SmokeFading` (24), case `0000:1A9D`, is implemented and host-tested.
It updates only Y, its fractional accumulator at byte 34, opacity, scale's
high byte, and vertical velocity. It does not decrement health or remove the
object. The case and its math helpers do not access global state.
See [SmokeFading](BehaviorRecovery.md#smokefading-object-local-rise-opacity-growth-and-deceleration)
and [instruction evidence](smoke-fading-evidence.txt).

Shared helper names are `AddFixedPoint8` (`10AC:384E`), `GetStepToward`
(`1E48:0A6C`), and `SignWord` (`1E48:0A25`). Their implementations in
[GameMath.cpp](Scaffold/GameMath.cpp) preserve parameter order, reference/word
widths, and original wrapping/edge behavior.

### Level height streams and WaterDrop

The renderer's seven-plane geometry layout matches the native 50x40 arrays.
Floor heights start at DS:`4A40`, relative room heights at `5210`; ceiling
presence and surface flags are also retained because the height queries use
them. Pascal one-based indexing accounts for the 51-byte bias in instruction
displacements. [Heightfield.cpp](Scaffold/Heightfield.cpp) loads unpacked
geometry and implements `1E48:1B45` (effective floor), `1E48:18CF` (terrain),
and `1E48:1BA6` (relative room height), including native fixed-point bias,
stacked-floor selection, and repeated-floor adjustment.

WaterDrop's case at `0000:2EBD` calls `10AC:9A2C`: old-velocity motion,
ceiling growth/wait, accelerated descent, a per-update splash countdown,
and floor-plus-room-height respawn. Gameplay mutations and the Drop sound
request are implemented; hardware playback needs a host audio backend. See
[Level heights and WaterDrop](BehaviorRecovery.md#level-heights-and-waterdrop)
and the exact [instruction evidence](heightfield-evidence.txt).

Surface-height metadata lives outside the geometry streams. Missing values
for slots 1..4 are explicit errors. The renderer names only three water
slots; the fourth slot, DS:`D4CC`'s complete role, and the loading source of
DS:`D4CE`'s repeated-floor spacing remain unresolved. No guessed defaults
are substituted for those surface slots.

### Sound effects and playback admission

The author confirms effect **5 = Drop**. `10AC:202A` actually consumes only
X/Z (`RETF 4`), returning Manhattan distance; `1E48:D001` converts that
distance to volume. The earlier effect word remains on the stack for
`1E48:D15C`, whose four arguments are **effect, volume, source ID, signed
per-source simultaneous-play limit** (`RETF 8`).

Playback chooses a random sample through `1E48:D086`, then scans exactly
four channels. It uses the last free one and **does not interrupt** occupied
channels. A negative limit additionally leaves one channel free; the limit
is not a priority. Source counts include all active samples from that source.

Initialization reads `samp\s_tab.prb`, rather than embedding the variant
references in code. The existing table has 129 five-byte records, each a
count plus four sample slots. Actual records use at most three variants;
Drop uses two, references **5 and 38**.

[Sound.h](Scaffold/Sound.h) and [Sound.cpp](Scaffold/Sound.cpp) implement the
enum, virtual audio interface, table loading, original random arithmetic,
attenuation, and channel/source policy. WaterDrop is wired to this API.
Host hardware mixing and sample decoding remain outside the library.
See [sound-effect contracts](BehaviorRecovery.md#sound-effects-attenuation-and-four-channel-admission)
and the bounded [instruction evidence](sound-evidence.txt).

### Typed game enums

[GameEnums.h](Scaffold/GameEnums.h) brings over the renderer's `BehaviorType`,
`CollisionType`, `DisplayType`, and `WeaponType` with their names, comments,
and numeric values. Behavior remains 16-bit, including the additional binary
selectors such as 300 and `FFFF`; the other three enums are byte-sized.
`RawGameObject` stores behavior/collision/display as these enum types.
Catalog entries reference enum members without repeating IDs, and handler
results carry enums rather than strings. Names are derived for console I/O.
The independent original-selector tests still cover every 16-bit value and
check the returned enum identity as well as the destination.

## Executable layout

**Observed and statically checked:**

| Property | Value |
| --- | --- |
| Format | DOS MZ |
| File size | 203,760 bytes |
| Header size / load module file offset | `0x2D40` |
| File-backed load module size | 192,176 bytes |
| Relocation table file offset | `0x001C` |
| Relocation entries | 2,888; all target words lie inside the file-backed load module |
| Bytes after the header-declared image | 0 |
| Header overlay number | 0 |
| Header initial SS, relative to load segment | `3E34` |
| Header initial SP | `4000` |

Neither the absence of trailing bytes nor overlay number zero proves that
the game has no overlay mechanism. Packing/compression has not been assessed.
Header stack values describe the loader's initial state, not necessarily the
stack used throughout gameplay.

Ghidra created ten initialized blocks named `CODE_0` through `CODE_9`, an
uninitialized block named `DATA`, and a separate header block. These are
**loader-generated divisions**, not recovered Pascal unit names or proof that
every byte in a `CODE_*` block is executable. The uninitialized block is not
an established layout of the game's globals.

**Observed and statically checked:**

| Address space | Entry |

The current Ghidra load segment is `1000`; it is not a measured DOS runtime
load segment. Its first instruction is a far call. The encoded operand is
`2CE4:0000` on disk and `3CE4:0000` after the loader applies relocation.

### Initial instruction sequence

The [import report](initial-import.txt) records eight consecutive far calls
at module-relative offsets `ED60`, `ED65`, `ED6A`, `ED6F`, `ED74`, `ED79`,
`ED7E`, and `ED83`. Later tracing established DS setup in the first callee;
the remaining roles are not fully determined.

The following instructions were decoded:

| Module-relative address | Instruction |
| --- | --- |
| `0000:ED88` | `ENTER 0x200, 0x0` |
| `0000:ED8C` | `MOV DI, 0xED42` |
| `0000:ED8F` | `PUSH CS` |
| `0000:ED90` | `PUSH DI` |

**Inferred:** some of the initial far calls may initialize Pascal units.
This is a lead, not an identification of any particular call.

**Resolved by subsequent byte inspection:** `CS:ED42` is the Pascal short string
`Patch` (`05 50 61 74 63 68`). It is passed to `1E48:0483` at `ED91`.
Nearby short strings are `Extrn`, `Game`, `Music`, and `Sounds`. The callee's
resource/archive semantics are not fully traced.

Ghidra's pseudo-disassembler can display far-call targets using physical
address aliases. For example, its `3000:ce40` has the same linear address as
the encoded `3CE4:0000`. Preserve the actual operand when reasoning about
the callee's logical CS and near addresses.
